# SolarLenes

React + Vite frontend integrated with the FastAPI backend. `/consumer` and `/ops` use actual backend authentication, authorized site lists, normalized energy or imported provider telemetry, history and reporting coverage. The original full workflow prototype remains separate at `/demo/`. All bundled datasets are synthetic.

## Run and edit

```sh
npm ci
npm run dev
npm test
npm run build
python3 database/seed.py
```

Run these commands from `frontend/`. During development, start the FastAPI backend from the repository root and visit `http://127.0.0.1:5173`; Vite proxies API requests to port 8000. For one-origin hosting, run `npm run build` first, start or restart FastAPI, and visit `http://127.0.0.1:8000/consumer`. See the [combined setup](../README.md) for importing provider data, creating accounts and granting access.

Connected mode accepts backend usernames such as `alice`, with their configured passwords. It has no public demo password or browser-selectable role. Sessions restore after reload, logout revokes the backend session, and metadata/telemetry refreshes every five seconds. API errors remain visible and never become mock data. Missing readings and AC/DC/phase boundaries remain distinct; charts preserve gaps and source cadence. Operations views use backend-authorized installations and area coverage, not browser seed scope.

- `src/main.jsx`: connected app entry and lazy workflow-demo routing.
- `src/connected.jsx`: API-backed login, customer/operations views, history, source health and account.
- `src/telemetry.js`: presentation of values, units, source status and chart series boundaries.
- `src/demo.jsx`: original browser-local workflow screens and role navigation.
- `src/styles.css`: responsive design, solar illustration, transitions and reduced-motion support.
- `src/domain.js`: seeded roles/sites, scope policy, plan arithmetic, safety ordering and crew eligibility.
- `src/store.js`: local persistence and media adapter; replace with an authenticated API.
- `database/schema.sql`: SQLite schema with foreign keys, client/site/inverter links, request routing, media references, sessions, reservations and audit records.
- `database/solarlenes-demo.sqlite`: seeded database, generated by `database/seed.py`.
- `database/fixtures.json`: the same fictional seed used by the frontend.
- `BACKEND_HANDOFF.md`: API, authorization, migration and implementation boundaries.

## Customer features

- **Plain-language energy**: today's export is translated into everyday equivalents (`src/friendly.js`), with separate wording for home and business accounts. Unknown energy is never shown as zero.
- **Energy chart periods**: Today, Weekly, Monthly and Yearly totals in kWh (`src/periods.js`). The connected app adds up measured history; the demo uses synthetic totals.
- **Production forecast**: `src/forecast.js` combines a live Open-Meteo weather forecast for Bucharest (sunshine, temperature, humidity; season through day length) with the installed capacity. Only that fixed city location is sent to the weather service. The formula and its assumptions are shown in the card.
- **Contract**: the customer saves supplier, fixed import/export prices and installed kWp; forecast values (and the demo planner) then use those prices instead of assumptions.
- **Looking after your home/business**: source reporting health in plain words, replacing the technical tables on the customer home (staff keep them under Sites).
- **Support**: connected customers send typed requests (13 request types) and follow-ups; staff reply under Requests. Text only, no video upload in connected mode.
- **Lessons**: short card-based lessons with a mini test. Passing earns a simulated bill credit once per lesson; in connected mode the server checks the answers.
- **Business accounts**: the backend account type (`home` or `business`) drives wording and comparisons. The demo adds `bistro@solarlenes.demo` (Bistro Soare, S04).

## Demonstration

1. Enter as Alex. Home shows synthetic energy flows, daily totals and a supported shortfall alert.
2. Plan a 6 kWh EV charge. The 13:00–15:00 suggestion estimates 4.50 RON; half solar estimates 2.25 RON. Edit the task and deadline, try another window, accept or cancel.
3. In Support, choose a request type and submit a synthetic description. The immediate-danger option creates a P0 PPC-triage report and reminds the customer to contact emergency services. Optional MP4/WebM clips are decoded in the browser and checked against 30 MB / 60 seconds.
4. Sign out and enter as Ioana. Open Virtual Visits to see Solar Care requests (the selected request type and priority are shown), reply, then sign in as the client to see the response. Grid, electrician, and billing requests appear only in their matching scoped worker queues; dispatchers/managers see their area's request queue.
5. Enter as the overall manager. Inspect all 24 sites: markers link each site to its demo inverter, and hovering/clicking a marker shows any linked client and inverter model. Filter radar and cases, confirm ownership, propose a qualified crew from a case, then confirm in Teams. Review the audit trail.
6. Account → Demo controls restores the initial dataset and clears local media. Reset is available only in the overall-manager interface.

Browser-local state is shared across tabs on the same origin. Session selection is per tab. Separate browser profiles do not share this demo state. A backend is required for separate devices, durable organizational storage and authenticated polling.

## Frontend scope and deliberate limits

Implemented: all five customer destinations; four operations views; six role types; typed request routing and worker-scoped inboxes; synthetic client/site/inverter links; local support/media/replies; safety-first cases and timelines; crew proposal/confirmation; account preferences; user activation; audit; seeded SQLite database; reproducible synthetic arithmetic; responsive layout.

Backend work remains: actual authentication, API-enforced scopes, shared database service, private media delivery/scanning, request rate limits, transactions/idempotency, five-second authorized polling, concurrent-safe fleet reservations, source adapters and continuous detection/replay. The SQLite file is a handoff artifact and is **not connected to the deployed static frontend**.

This version uses JavaScript React with a typed integration contract, rather than separate TypeScript applications. It supports contiguous tasks only, one accepted task per installation, a fixed-price solar scenario, and predefined eight incident families. It does not implement split EV profiles, live telemetry, billing, tariff-indexed contracts, a fitted forecast, physical control, automatic failure detection, route optimization or actual emergency response. Offer previews are not capacity reservations; accepted plans reserve full power in the local simulation. Browser writes are not multi-client transactions. Real-world accuracy, avoided visits and earned savings are not claimed.

The CSS uses optional Google Fonts with local font fallbacks; all functional assets are bundled. The technical design assumes Europe/Bucharest; the fixed replay uses 14 November 2026 at 13:00 EET. Audit receipt times use actual UTC. This is not a DST scheduling engine.

## Making a virtual visit a live call

The current “Virtual Visits” feature is a shared, asynchronous ticket and technician reply; it does not place calls. For a real two-browser demo, use a hosted WebRTC service such as LiveKit Cloud (or Twilio Video):

1. Create a project and keep its API secret in a backend environment variable. The browser must never receive the service secret.
2. Add an authenticated endpoint such as `POST /api/visits/{id}/call`. Check the caller's ticket/site access and consent, create or reuse a room named from the ticket ID, then mint short-lived join tokens for the customer and assigned worker. Return only the room URL and that participant's token.
3. Add a “Start call” action in the client request and worker inbox. The React app joins with the provider's WebRTC client/components; the browser asks for camera/microphone permission. Offer explicit mute/camera-off controls and a text-only fallback.
4. Serve the app and API over HTTPS (secure media permissions require it; `localhost` is allowed for development). A hosted SFU/relay handles signaling, ICE negotiation and TURN fallback so callers behind restrictive routers can connect.
5. Verify provider webhooks on the backend to record call started/ended and duration on the ticket. Keep recording disabled unless every participant separately consents; if enabled, use private storage and a stated retention/deletion policy.

The static Vite app and `localStorage` are not enough for calls between devices: this needs the authenticated backend, a token endpoint, and the video provider. Use only synthetic demo data, and never present the call workflow as emergency response.
