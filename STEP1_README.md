# One-view solar: synthetic inverter datasets + one universal scraper (Step 1)

> **SYNTHETIC DEMONSTRATION.** Every payload in this repository is generated by `generate_demo.py`.
> The data are shaped after pinned public references (see [SOURCE_NOTES.md](SOURCE_NOTES.md)). They are **not**
> real Huawei, Fronius or SolarEdge customer data, not measured households and not vendor output. Every
> statistic in the reports describes this synthetic replay only. None of it is a field-accuracy or legal/API
> compliance claim.

This is Step 1 of a Romanian prosumer hackathon prototype. It gives you:

* **Three provider datasets that differ the way the documented interfaces differ:** Huawei FusionSolar SmartPVMS
  Northbound (device types 38/39), Fronius Solar API V1 (PowerFlow + CommonInverterData, SnapInverter vs GEN24) and
  SolarEdge Monitoring API (technical telemetry, currentPowerFlow, storageData). That is 9 fictional sites over
  7 local days (15–21 July 2026, Europe/Bucharest). The data come from a one-minute latent physical simulation with
  injected delivery defects and real-looking physical conditions.
* **One shared ingestion engine** (`scraper.py` + `engine/`). Provider differences live only in
  `config/provider_profiles.yaml`. The engine has no provider classes or `if provider == ...` branches, and a test
  enforces this.
* **Canonical, measurement-level output** in SQLite plus CSV/JSON. It includes an auditable quality report, an HTML
  demo report and pytest tests.

The two downstream apps (the customer app and the PPC operations app with maintenance/junior/senior scopes) are
**not** built here. Provider/account/site/device identity is preserved so their authorisation can work.
`sites.json` keeps platform role scopes separate from manufacturer access.

## Quick start (offline, no credentials, no network)

```bash
pip install -r requirements.txt
python generate_demo.py --seed 42 --sites-per-provider 3 --start 2026-07-15 --days 7 --out demo_data
python scraper.py --config config/provider_profiles.yaml --input demo_data --out build --as-of 2026-07-22T00:00:00+03:00
python scraper.py --config config/provider_profiles.yaml --input demo_data --out build --as-of 2026-07-22T00:00:00+03:00
pytest -q
```

* Generation takes about 35 s. The first ingestion takes about 3 min (380k observations). The second run skips all
  39,722 already-committed deliveries and only re-exports reports (about 1.5 min). `pytest -q` (68 tests) takes about
  4–5 min: it regenerates and re-ingests everything in a temp folder.
* Tested with **Python 3.10.11** on Windows (the only interpreter on the build machine). The spec asked for 3.11+;
  the code uses no 3.11-only features and should run on 3.10–3.13.
* Optional HTTP replay (loopback only, after the offline path):
  ```bash
  python mock_server.py --input demo_data --files huawei/delivery/getDevRealKpi.ndjson --port 8765
  python scraper.py --config config/provider_profiles.yaml --input demo_data --out build_http --as-of 2026-07-22T00:00:00+03:00 --http http://127.0.0.1:8765 --side-datasets ""
  ```

## What is generated

| Path | Content |
| --- | --- |
| `demo_data/<provider>/delivery/*.ndjson` | Native payloads as delivered, **with injected defects**. One mock-transport envelope per line wraps one native payload. |
| `demo_data/<provider>/clean_reference/*.ndjson` | The same latent data without injections, kept for comparison tests (`--dataset clean_reference`). |
| `demo_data/<provider>/manifest.json`, `demo_data/manifest.json` | Source manifests with sha256 checksums. The engine verifies them and refuses a mismatching file. |
| `demo_data/sites.json` | Registered account/site/device bindings, timezone, declared capabilities, platform role scopes, and a manufacturer access *reference* (no secrets). |
| `demo_data/regulatory_metadata.json` | Separate, regulatory-**inspired** synthetic technical data per site (Order 228/2018 context). Not a certificate and not from any API. |
| `demo_data/golden_cases/` | Cross-provider golden case: 4.2 kW vs 4,200 W AC output at one instant, plus a hybrid DC `P_PV`. |
| `demo_data/dst_cases/` | Europe/Bucharest DST edge cases (2026-03-29 gap, 2026-10-25 repeated hour). |
| `tests/ground_truth/`, `tests/injection_manifest.json` | **Evaluation-only** hidden truth and labels. The engine refuses to read anything under `tests/`, `ground_truth` or `injection_manifest.json`. |

 "payload": {"Body": {"Data": {"Inverters": {...}, "Site": {"P_Grid": -1234.5, ...}}}, "Head": {"Timestamp": "...+03:00", ...}}}

## Architecture

```
manifest / mock HTTP ─► transport ─► Ingestor.process_line (same for every profile)
   envelope → binding (registered site) → route (profile+endpoint+variant from YAML) → transport status
   → provider failure envelope → empty/unsupported → record iteration → identity + time roles
   → dedupe / conflict → field mapping (closed transform library) → bounds → SQLite
derive.recompute (counters, estimated power integration) → health (replay clock) → review (demo policies)
report (quality_report.json, CSV/JSONL, HTML)
```

* Transform library (closed, validated at load): `numeric`, `value_object`, `sign_split`, `negate`, `edge_flow`,
  `state`. Derivations: `counter_difference`, `power_integration`. There is no eval/exec, no generated code and no LLM.
* A fourth tiny provider (`acme_demo`, decimal comma) is added **by config only** in
  `tests/test_architecture.py::test_fourth_provider_is_config_only`. The test asserts the engine files are
  byte-for-byte unchanged. That shows extensibility within the supported transform language, not universal
  compatibility.

## Repaired vs normalised vs unresolved

* **Routine normalisation, not repair:** W→kW, Wh→kWh, documented sign splitting (Fronius `P_Grid`/`P_Akku`,
  SolarEdge `storageData.power`), edge-directed flows. These are counted in `routine_transform_counts`.
* **Deterministic transformations, audited per value:** numeric strings in the profile's allowed format, a
  declared unit change (kW→W), a registered mapping-version alias.
* **Defects repaired:** exact duplicate deliveries are suppressed (kept as raw evidence and counted once).
  Backfilled windows are merged by source time.
* **Quarantined, with raw evidence kept:** a truncated NDJSON line, a truncated JSON body, a missing device id,
  an unusable or ambiguous/nonexistent local time, and an unregistered binding or device.
* **Unresolved on purpose:** a 1000x spike without unit evidence (value withheld, never divided), a decimal-comma
  value under a dot-decimal profile, SOC out of range (never clamped), conflicting versions (both kept, excluded
  from frames and counters), the lifetime-counter reset crossing interval (unknown), trailing/denied/stale gaps (no
  interpolation, no zeros), and unknown fields (sent to review).

## Seven-step demo walkthrough (`build/demo_report.html`)

1. **Native payloads:** one Huawei `dataItemMap` item, one Fronius GEN24 PowerFlow and one SolarEdge record, each
   with its canonical observations and time role.
2. **Exact duplicate:** the original delivery against the re-delivery. The re-delivery is kept as evidence and
   commits zero observations.
3. **Counter reset:** S3 `totalEnergy` drops. The crossing interval is `unknown_counter_reset` and the following
   intervals are valid again. The local-midnight daily resets are counted separately.
4. **Stale / denied feeds:** H2 is stale against the replay clock. S3 `storageData` was denied for a day (403),
   kept distinct from a 400 time-range error and a 429. F3 has a frozen logger.
5. **Unit ambiguity:** H2 `active_power` arrives at 1000x without a unit change. The value is withheld as invalid
   with its original preserved. A decimal-comma value is not guessed.
6. **Physical review candidates:** the H1 inverter temperature peaks above 70 °C and the evidence observation is
   unchanged. The H2 phase voltage goes above 253 V, and the S2 peer underproduction starts on 19 July. The overcast
   day (18 July) and nights produce no candidates.
7. **4,200 W = 4.2 kW:** Huawei `active_power`, Fronius SnapInverter `Inverters.1.P` and SolarEdge
   `totalActivePower` all become `inverter_ac_output_kw = 4.2` on the same boundary. The GEN24 `P_PV` stays
   `pv_dc_kw`, and the hybrid AC output (3.95 kW) is not equated with it.

## Known limitations (honest scope)

* Synthetic only. No live endpoint was called, and the field evidence comes from public references and mirrors.
  Huawei failCodes and Fronius `Head.Status`/`StatusCode` mappings are flagged `verified: false`. The Huawei
  battery power sign is an **assumed_demo** convention.
* The Huawei meter endpoint is not modelled, so household load and grid exchange stay unavailable for Huawei sites.
  They are never inferred from inverter output.
* SolarEdge PV in `currentPowerFlow` is mapped to `pv_production_kw` with an **unspecified** boundary, not to
  `pv_ac_kw`.
* Power-integrated energies (Fronius/SolarEdge flows) are `estimated` from snapshots. They are not billing-grade.
* `stale` availability at observation level applies to real-time responses that lag their capture time. A frozen
  logger repeating identical content is counted once and reported as a stale feed and gap.
* Peer-based underproduction compares sites that share one synthetic weather. It is a demo policy, not a fault
  diagnosis. None of the review thresholds are manufacturer or grid-code limits, and nothing is ever sent to a
  device.
* Regulatory metadata is an illustrative subset. Its field-level legal applicability is unverified, so confirm
  with the mentor/DSO before any deployment.
* Performance: a single-process Python + SQLite design is fine for this demo (380k observations in about 3 min).
