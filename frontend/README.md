# SolarLenes

React + Vite frontend integrated with the FastAPI backend. `/consumer` and `/ops` use actual backend authentication, authorized site lists, normalized energy or imported provider telemetry, history and reporting coverage. The original full workflow prototype remains separate at `/demo/`. All bundled datasets are synthetic.

## Run and edit

```sh
npm ci
npm run dev
npm test
npm run build
python3 database/seed.py
```

Run these commands from `frontend/`. During development, start the FastAPI backend from the repository root and visit `http://127.0.0.1:5173`; Vite proxies API requests to port 8000. For one-origin hosting, run `npm run build` first, start or restart FastAPI, and visit `http://127.0.0.1:8000/consumer`. See the [combined setup](../README.md) for importing provider data, creating accounts and granting access.

Connected mode accepts backend usernames such as `alice`, with their configured passwords. It has no public demo password or browser-selectable role. Sessions restore after reload, logout revokes the backend session, and metadata/telemetry refreshes every five seconds. API errors remain visible and never become mock data. Missing readings and AC/DC/phase boundaries remain distinct; charts preserve gaps and source cadence. Operations views use backend-authorized installations and area coverage, not browser seed scope.

- `src/main.jsx`: connected app entry and lazy workflow-demo routing.
- `src/connected.jsx`: API-backed login, role menus, customer/operations views, history, source health and account.

- `src/video.js`: support video rules (MP4/WebM, 30 MB, 60 s) and readable sizes.
- `src/telemetry.js`: presentation of values, units, source status and chart series boundaries.
- `src/demo.jsx`: original browser-local workflow screens and role navigation.
- `src/map.jsx`: `BucharestMap`, a real OpenStreetMap street map of Bucharest (plain Leaflet) with zoom/pan and site markers; reusable with plain site data.
- `src/ops.jsx` / `src/ops.css`: reusable staff components: `FleetForecast`, `RevenueView`, `AssignmentReport`, `CrewSummary`.
- `src/dispatch.js`: pure crew assignment rules (eligibility, assign by severity, send team, meetings, resolve, teams report, technician area).
- `src/revenue.js`: pure revenue estimate from synthetic billing profiles × tariff.

- `src/domain.js`: seeded roles/sites, scope policy, plan arithmetic, safety ordering and crew eligibility. ## Customer features

- **Plain-language energy**: today's export is translated into everyday equivalents (`src/friendly.js`), with separate wording for home and business accounts. Unknown energy is never shown as zero.
- **Energy chart periods**: Today, Weekly, Monthly and Yearly totals in kWh (`src/periods.js`). The connected app adds up measured history; the demo uses synthetic totals.
- **Production forecast**: `src/forecast.js` combines a live Open-Meteo weather forecast for Bucharest (sunshine, temperature, humidity; season through day length) with the installed capacity. Only that fixed city location is sent to the weather service. The formula and its assumptions are shown in the card.
- **Contract**: the customer saves supplier, fixed import/export prices and installed kWp; forecast values (and the demo planner) then use those prices instead of assumptions.
- **Looking after your home/business**: source reporting health in plain words, replacing the technical tables on the customer home (staff keep them under Sites).
- **Support**: connected customers send typed requests (13 request types) and follow-ups; staff reply under Requests. An optional short video (MP4 or WebM, at most 30 MB and 60 seconds) can be attached: type and size are checked first, then the duration is read from the file's metadata in the browser (the server re-checks type, size and file signature). The request is created first and the video uploaded to it; if the upload fails the request still exists and the customer can retry with **Attach a video** in the support history. Video is off for immediate-danger reports. The history plays attached videos and shows a meeting booked by a technician (Bucharest time and crew).
- **Lessons**: short card-based lessons with a mini test. Passing earns a simulated bill credit once per lesson; in connected mode the server checks the answers.
- **Business accounts**: the backend account type (`home` or `business`) drives wording and comparisons. The demo has seven business sites from the shared fixture (offices, a warehouse, factories, a supermarket and two bistros); `bistro@solarlenes.demo` (Bistro Soare, S04) is the business login.

## Staff features (connected app)

Menus by role (first entry is the landing page):

| Role | Pages |
| --- | --- |
| Supervisor (overall or area manager; the server scopes the data) | Area Radar, Incidents, Teams, Revenue, Sites, History, Account |
| Dispatcher | Area Radar, Incidents, Teams, Requests, Sites, History, Account |
| Technician | Incidents, Requests, Sites, History, Account |
| Customer | Home, History, Support, Learn, Account |

On phones the bottom bar shows four pages plus **More** (opens the full menu) when a role has more than five.

- **Area Radar**: the Bucharest map from `/ops/map` (open incident → tier marker; otherwise a recent feed → ✓; anything else → stale). A site with open incidents opens the Incidents page filtered to that site; other sites open the installation detail. Sites without a profile (for example imported provider sites) are not on the map and a note says how many. The fleet forecast uses `/ops/capacity`. The real telemetry coverage cards stay below.
- **Incidents**: server severity order, open/all and tier filters, and a detail dialog with evidence, source, assignment, a linked customer request and the **Incident log**. Dispatcher: assign an eligible crew (busy crews shown disabled), **Assign automatically**, **Mark resolved**, and **Assign by severity** for the whole scope with assigned/skipped results in plain words. Technician: **Send the team**, **Allocate meeting** (date, start and end in Bucharest time, converted to UTC; at most 4 hours; overlaps are refused by the server) and **Mark resolved** when his crew has the case. Supervisor: read-only plus **Mark resolved**.
- **Teams**: assignment report by incident (with "Not assigned" rows for open incidents without a crew), crew summary, and for the dispatcher the assignment tools lower on the page.
- **Revenue** (supervisor): the server's monthly estimate and basis sentence; no money is recomputed in the browser.
- **Requests** (dispatcher, technician): attached videos play inline, booked meetings are shown, and each request links to its incident (and back).
- Views poll every five seconds; unchanged responses keep their references, so the map is not rebuilt. 401 signs out; a 403/404 is shown as a message and stops that view's polling.

## Staff features (workflow demo)

- **Bucharest map**: Area Radar shows a real OpenStreetMap street map with zoom and pan. Business sites are larger squares, homes are circles; colour shows status and a letter repeats it (✓ no open incident, – stale telemetry, P0–P3 open incident). A click opens a popup with zone, segment/business type, kWp and status. The installations are fictional and only placed near real neighbourhoods: business sites on industrial platforms and commercial zones, most homes in residential neighbourhoods, few sites in the historic centre. Without network tiles the markers stay on a plain background.
- **Fleet production forecast**: the live city weather forecast × the summed installed kWp of the sites in scope, per area and total, for today, tomorrow and day 3, with the formula disclosed.
- **Teams**: a read-only assignment report by incident (tier, site, area, crew, dispatch/meeting, status, who assigned, when) and a per-crew summary (members, availability, open/completed by tier). The overall manager and the area manager read the same data; the area manager sees his area's subset. Below the report, the PPC dispatcher assigns an eligible, available crew manually or with **Assign by severity** (P0, P1, P2, P3; oldest first; until no crew is free; skipped incidents are listed with the reason). Billing questions are never given to a crew.
- **Technician actions**: a technician sees every incident in his crew's area. On an incident he can **Send the team** (crew becomes unavailable), **Allocate meeting** (date, start/end; overlapping meetings for the crew are refused; the customer sees the booking on their request) and **Mark resolved** (frees the crew).
- **Revenue**: estimated monthly net revenue = energy sold to customers (import kWh × import price) + service fees − payments for exported solar (export kWh × export price). Saved contract prices are used where present, otherwise the fixture's default tariff. Shows the business vs home split, revenue by area and a ranked table of business accounts. This is an estimate from synthetic billing profiles, not invoices.
- **Incident log**: status changes, owner confirmations, assignments, team sent, meetings, replies and customer follow-ups are written to the incident's own log. There is no separate audit page.

## Demonstration

1. Enter as Alex. Home shows synthetic energy flows, daily totals and a supported shortfall alert.
2. Plan a 6 kWh EV charge. The 13:00–15:00 suggestion estimates 4.50 RON; half solar estimates 2.25 RON. Edit the task and deadline, try another window, accept or cancel.
3. In Support, choose a request type and submit a synthetic description. The immediate-danger option creates a P0 PPC-triage report and reminds the customer to contact emergency services. Optional MP4/WebM clips are decoded in the browser and checked against 30 MB / 60 seconds.
4. Enter as the PPC dispatcher (North). Area Radar shows only the North sites on the Bucharest map and the North fleet forecast. In Teams, press **Assign by severity**: the P1 incident gets Solar Care and the rest are listed as skipped (no crew free). Billing requests appear in his Virtual Visits; he answers them.
5. Enter as Ioana. Incidents shows every North incident and her crew's status. Open the assigned case and **Send the team**; open Alex's request and **Allocate meeting** (a second overlapping booking is refused); then **Mark resolved** on the first case to free the crew. Virtual Visits lists the Solar Care requests; replies are shown to the client.
6. Sign in as Alex: Support history shows the booked meeting on the request. Open the incident to read its log.
7. Enter as the area manager: only North on the map, cards, forecast, incidents, Teams and Revenue. Enter as the overall manager: all areas; the North rows in Teams are the same as the area manager's. Revenue shows the business vs home split and the ranked business accounts.
8. Account → Demo controls (overall manager only) restores the initial dataset and clears local media.

Browser-local state is shared across tabs on the same origin. Session selection is per tab. Separate browser profiles do not share this demo state. A backend is required for separate devices, durable organizational storage and authenticated polling.

## Frontend scope and deliberate limits

Implemented: all five customer destinations; five operations views (Area Radar with a Bucharest street map and fleet forecast, Incidents, Virtual Visits, Teams, Revenue); five role types; typed request routing and worker-scoped inboxes; synthetic client/site/inverter links; local support/media/replies; safety-first cases with incident logs; crew assignment by severity, send team, customer meetings and resolution; revenue estimate; account preferences; seeded SQLite database; reproducible synthetic arithmetic; responsive layout.

Backend work remains: actual authentication, API-enforced scopes, shared database service, private media delivery/scanning, request rate limits, transactions/idempotency, five-second authorized polling, concurrent-safe fleet reservations, source adapters and continuous detection/replay. The SQLite file is a handoff artifact and is **not connected to the deployed static frontend**.

This version uses JavaScript React with a typed integration contract, rather than separate TypeScript applications. It supports contiguous tasks only, one accepted task per installation, a fixed-price solar scenario, and predefined eight incident families. It does not implement split EV profiles, live telemetry, billing, tariff-indexed contracts, a fitted forecast, physical control, automatic failure detection, route optimization or actual emergency response. Offer previews are not capacity reservations; accepted plans reserve full power in the local simulation. Browser writes are not multi-client transactions. Real-world accuracy, avoided visits and earned savings are not claimed.

The CSS uses optional Google Fonts with local font fallbacks; all functional assets are bundled except the OpenStreetMap tiles on the staff map (loaded from tile.openstreetmap.org; only map tile coordinates are requested, attribution shown) and the Open-Meteo forecast. The technical design assumes Europe/Bucharest; the fixed replay uses 14 November 2026 at 13:00 EET. Incident log times use actual UTC. This is not a DST scheduling engine.

## Making a virtual visit a live call

The current “Virtual Visits” feature is a shared, asynchronous ticket and technician reply; it does not place calls. For a real two-browser demo, use a hosted WebRTC service such as LiveKit Cloud (or Twilio Video):

1. Create a project and keep its API secret in a backend environment variable. The browser must never receive the service secret.
2. Add an authenticated endpoint such as `POST /api/visits/{id}/call`. Check the caller's ticket/site access and consent, create or reuse a room named from the ticket ID, then mint short-lived join tokens for the customer and assigned worker. Return only the room URL and that participant's token.
3. Add a “Start call” action in the client request and worker inbox. The React app joins with the provider's WebRTC client/components; the browser asks for camera/microphone permission. Offer explicit mute/camera-off controls and a text-only fallback.
4. Serve the app and API over HTTPS (secure media permissions require it; `localhost` is allowed for development). A hosted SFU/relay handles signaling, ICE negotiation and TURN fallback so callers behind restrictive routers can connect.
5. Verify provider webhooks on the backend to record call started/ended and duration on the ticket. Keep recording disabled unless every participant separately consents; if enabled, use private storage and a stated retention/deletion policy.

The static Vite app and `localStorage` are not enough for calls between devices: this needs the authenticated backend, a token endpoint, and the video provider. Use only synthetic demo data, and never present the call workflow as emergency response.
